02

What Is Pipecat

Pipecat is an open-source Python framework for building real-time, low-latency voice and multimodal AI agents — the kind of thing you need when a human is talking to a bot live over audio (or video), rather than typing into a chat box. It's built by the team behind Daily.co and is transport-agnostic: it can run over WebRTC (LiveKit, Daily, WebSocket) or plain telephony.

The core idea is a pipeline of frame processors. Every unit of data — a chunk of audio, a transcribed sentence, an LLM token, a DTMF keypress, a "start speaking now" signal — is wrapped in a Frame object and pushed through an ordered list of FrameProcessors, exactly the way audio moves through a mixing desk: each stage can read a frame, transform it, drop it, or pass it straight through, before handing it to the next stage.

Frames travel in two directions: downstream (the normal direction — mic audio in, spoken reply out) and upstream (control signals that need to go back toward the input side, like telling the STT service to switch languages). This bidirectional design is what lets a processor sitting in the middle of the chain, like our IVRGate, reconfigure services on either side of it.

Pipecat deliberately keeps the services layer pluggable: STT, LLM, and TTS are each just an interface, so swapping Sarvam for Deepgram, or Groq for OpenAI, is a one-line change in services/*.py with no change to the pipeline shape. On top of the raw pipeline it also ships turn-taking primitives (VAD, "Smart Turn" end-of-speech detection), conversation-context aggregation, and function/tool calling — all of which this project uses directly.

Why this matters for voice specifically: in a text chatbot you can wait for the whole message. In a phone call, audio is continuous and the bot must decide, in real time, when the caller has actually finished a turn, when to start talking over silence, and how to keep latency low enough that the conversation doesn't feel like a satellite phone call. Pipecat's frame pipeline plus VAD/turn-strategy layer exists specifically to solve that problem.
03

Every Pipecat Import, Explained

Grouped by what each import is responsible for, in the order they appear across core/pipeline.py, core/transport.py, core/ivr.py, core/languages.py, core/tool.py, and services/*.py.

Pipeline runtime
pipecat.pipeline.pipeline

Pipeline

The container class that takes an ordered Python list of processors/services and wires each one's output into the next one's input. This is literally the list built at the bottom of create_pipeline() — transport.input() through context_aggregator.assistant().

pipecat.pipeline.worker

PipelineWorker

Wraps a built Pipeline so it can be scheduled and supervised like a job/worker rather than a bare object — handles its own start/stop lifecycle and error boundaries independent of the rest of the process.

pipecat.workers.runner

WorkerRunner

The top-level event loop driver. runner.add_workers(worker) registers the pipeline worker onto a shared task/message bus, and runner.run() blocks the process, actually pumping frames until the call ends — this is what main.py awaits to "keep the bot alive."

LiveKit transport
pipecat.transports.livekit.transport

LiveKitTransport, LiveKitParams

The bridge between Pipecat and a LiveKit room. LiveKitParams(audio_in_enabled=True, audio_out_enabled=True) turns on mic capture and speaker playback. The transport object exposes .input() and .output() as pipeline processors — they're the very first and near-last steps in the chain, converting between LiveKit's WebRTC audio tracks and Pipecat's internal audio frames.

pipecat.runner.livekit

generate_token_with_agent

Builds the signed LiveKit access token the bot itself uses to join the room as a participant named "scheme-setu-bot" — separate from the caller's own token, which is minted by voice_server.py's /token endpoint or generate_token.py for manual testing.

Turn-taking & VAD (deciding when the caller is "done talking")
pipecat.audio.vad.silero

SileroVADAnalyzer

Wraps the Silero voice-activity-detection model — a small neural net that classifies short audio windows as speech vs. silence. This is the raw signal everything else (turn start, turn stop, barge-in) is built on top of.

pipecat.audio.vad.vad_analyzer

VADParams

Tuning knobs for the analyzer. Here only stop_secs=0.8 is set — the caller must go quiet for 0.8 seconds before Silero reports "speech ended," which avoids cutting people off mid-sentence during natural pauses.

pipecat.processors.audio.vad_processor

VADProcessor

The pipeline-facing wrapper around the analyzer. It sits right after transport.input(), watches the raw audio frames flowing past, and emits speech-started / speech-stopped events into the pipeline for downstream processors (like the context aggregator) to react to.

pipecat.turns.user_start

VADUserTurnStartStrategy

One of possibly several strategies for deciding when a user's turn begins. Configured here as the only start trigger, meaning a turn only starts when VAD detects the mic picking up speech — not, say, on some other heuristic.

pipecat.turns.user_turn_strategies

UserTurnStrategies, default_user_turn_stop_strategies

UserTurnStrategies bundles the start + stop rules together. The stop side uses Pipecat's built-in defaults, which combine VAD silence with a "Smart Turn" model that also considers sentence-completion cues (not just silence) — so a caller pausing to think mid-sentence is less likely to trigger a premature reply.

Context & memory
pipecat.processors.aggregators.llm_context

LLMContext

The actual conversation memory object: a running messages list plus the tools schema the LLM is allowed to call. One instance is created in create_pipeline() and shared by reference across the IVR gate and both aggregators — so "baking in" the language directive once (in ivr.py) is visible everywhere for the rest of the call.

pipecat.processors.aggregators.llm_response_universal

LLMContextAggregatorPair, LLMUserAggregatorParams

Produces two complementary processors from one shared context: .user(), placed before the LLM, which buffers/finalizes the caller's transcribed speech into a proper "user" message using the turn strategies above; and .assistant(), placed after TTS/transport-output, which writes the LLM's reply back into the same context as an "assistant" message so the next turn has full history.

Frames & base processor classes
pipecat.processors.frame_processor

FrameProcessor, FrameDirection

The base class every custom pipeline stage extends — IVRGate is one. Subclassing it means overriding process_frame(frame, direction) and calling self.push_frame(...) to forward (or withhold) frames. FrameDirection is the DOWNSTREAM / UPSTREAM enum used to pick which way a frame travels next.

pipecat.frames.frames

StartFrame, InputDTMFFrame, TTSSpeakFrame, TTSUpdateSettingsFrame, STTUpdateSettingsFrame, TranscriptionFrame, InterimTranscriptionFrame

The concrete frame types the IVR gate cares about: StartFrame fires once when the pipeline boots (used to trigger the spoken menu); InputDTMFFrame carries a caller's phone keypress; TTSSpeakFrame forces a specific line to be spoken immediately; TTSUpdateSettingsFrame / STTUpdateSettingsFrame hot-swap the TTS/STT language mid-call; TranscriptionFrame / InterimTranscriptionFrame are final and partial speech-to-text results.

pipecat.frames.frames

FunctionCallResultProperties

Metadata attached to a tool result telling Pipecat what to do next — here, run_llm=True tells it to immediately re-invoke the LLM with the tool's output appended, so the model can speak the answer without waiting for a new user turn.

Model services (STT / LLM / TTS)
pipecat.services.sarvam.stt

SarvamSTTService

Speech-to-text via Sarvam AI's saaras:v3 model, tuned for Indian languages and auto language detection. Configured in services/stt.py, re-tuned live by the IVR gate once a language digit is pressed.

pipecat.services.sarvam.tts

SarvamTTSService

Text-to-speech via Sarvam's bulbul:v3-beta model — voice "aditya", default language Hindi, pace=1.1 for a slightly brisker conversational cadence. Same service class is also driven directly by the IVR gate to speak each menu line in its own language.

pipecat.services.groq.llm

GroqLLMService

The reasoning/response engine, running Groq's hosted openai/gpt-oss-20b. Capped to max_completion_tokens=512 and reasoning_effort: low specifically to keep per-turn latency low on a live call — a 512-token ceiling and minimal internal "thinking" trades a bit of depth for the seconds that matter on a phone.

Tool calling (LLM → retrieval bridge)
pipecat.adapters.schemas.function_schema / tools_schema

FunctionSchema, ToolsSchema

Declare the search_schemes function (name, description, JSON-schema parameters query / state / government_level) in a shape the LLM's function-calling API understands, then bundle it into a ToolsSchema that's attached straight onto the shared LLMContext.

pipecat.services.llm_service

FunctionCallParams

What the LLM service hands to your registered handler when the model decides to call the tool — the parsed arguments plus a result_callback used to hand the answer back into the running conversation.

llm.register_function(...)

register_scheme_tool(llm)

Not a Pipecat import itself, but the wiring call in core/tool.py that binds the search_schemes name to the _handle_search coroutine on the GroqLLMService instance, so the framework knows what code to run for that tool name.

Supporting enums (used to drive the IVR gate)
pipecat.audio.dtmf.types

KeypadEntry

Enum for phone keypad digits (ONE, TWO, THREE…). languages.py keys its language map off this enum so a raw DTMF frame can be looked up directly.

pipecat.transcriptions.language

Language

Enum of language codes (Language.HI, EN, TA) used both as the TTS default and as the value baked into TTSUpdateSettingsFrame/STTUpdateSettingsFrame when the IVR gate locks a language.

04

How The Voice Agent Actually Works

End-to-end walkthrough of one phone call, tracing exactly what the code does, in order.

Call lifecycle — boot to first word
voice_server.py / main.py

A room is created, and two tokens exist

The caller's browser/app hits GET /token to get a LiveKit access token for room "support-room". Separately, the bot process calls configure_transport(room_name), which mints its own token via generate_token_with_agent(...) under the identity "scheme-setu-bot" — the caller and the bot are two independent participants in the same LiveKit room.

core/transport.py

The transport is configured

LiveKitParams(audio_in_enabled=True, audio_out_enabled=True) turns on both directions of audio, and a LiveKitTransport is constructed with the room URL, the bot's token, and those params — this object is what create_pipeline() will later plug in as the very first and near-last pipeline stage.

core/pipeline.py

create_pipeline() assembles every stage once

STT, TTS and LLM services are configured; the scheme-search tool is registered on the LLM; a single LLMContext is created with the system prompt and tool schema; the IVRGate is built around that same context object; the LLMContextAggregatorPair is built with VAD-start / Smart-Turn-stop turn strategies; and a VADProcessor wraps Silero with an 0.8s stop threshold. All nine stages are then handed to Pipeline([...]) in the exact order shown in the diagram above.

core/pipeline.py → main.py

The pipeline is handed to the runner

The Pipeline is wrapped in a PipelineWorker, registered onto a WorkerRunner via add_workers, and runner.run() is awaited — this is the call that actually keeps the process alive and pumping frames for the whole duration of the call.

core/ivr.py

The very first frame triggers the language menu

The instant the pipeline starts, a StartFrame reaches IVRGate before anything else does. It responds by pushing a TTSSpeakFrame for each language in languages.py, in that language's own voice — "हिंदी के लिए एक दबाएं," then "For English, press two," then the Tamil line — and starts a 6-second timeout watch.

The IVR language gate, in detail

IVRGate is the one fully custom FrameProcessor in this system, and it sits deliberately between STT and the context aggregator so it can intercept transcribed speech before it ever reaches the LLM. Its job is a one-time language lock, then it gets out of the way for the rest of the call:

  • Before a language is chosen: any TranscriptionFrame or InterimTranscriptionFrame is silently dropped — a caller talking over the menu can't accidentally start a conversation with the LLM before picking a language. InputDTMFFrame keypresses are handled and consumed (never forwarded raw).
  • On a valid digit: _lock() runs once. It (1) appends a language directive (e.g. "Reply only in Hindi, in Devanagari script") straight onto the shared LLMContext.messages — a single system message, not a per-turn injection, so the LLM never has to re-detect language; (2) pushes a TTSUpdateSettingsFrame downstream to retune Sarvam TTS, since TTS sits after this gate in the chain; and (3) pushes an STTUpdateSettingsFrame upstream to retune Sarvam STT, since STT sits before this gate — this is the clearest example in the codebase of why Pipecat frames need a direction at all.
  • On an invalid digit or silence: a retry counter increments, the menu replays, and the timeout restarts — up to IVR_MAX_RETRIES (2) times, after which it force-locks to DEFAULT_DIGIT (Hindi) rather than stalling the call forever.
  • Once locked: self._locked flips true and every frame is simply passed straight through — the gate becomes a no-op for the remainder of the call.

Because languages.py is the single source of truth (digit → name → TTS language → menu line → system directive), adding a fourth language means adding one dict entry — nothing else in ivr.py, pipeline.py, or the prompt needs to change.

The tool-call round trip
core/prompt.py + core/tool.py

The system prompt forces tool-first answers

SYSTEM_PROMPT instructs the model to call search_schemes for any question about schemes and never to invent one — this is enforced entirely through prompt instructions, since a Groq function-calling model decides for itself when to invoke a registered tool.

core/tool.py → services/llm.py

The LLM emits a function call, Pipecat routes it

When the model decides to call search_schemes, GroqLLMService matches the name against what register_scheme_tool(llm) registered, and invokes _handle_search(params: FunctionCallParams) with the parsed query, state, and government_level arguments.

core/tool.py → retrieval/retriever.py

The actual search runs off the event loop

search_schemes(...) does blocking network I/O against Cloudflare (for embeddings) and Qdrant (vector search), so it's dispatched via asyncio.to_thread(...) — keeping the audio pipeline's event loop free so the call doesn't stutter while the lookup runs. Results are trimmed hard (each field capped to 200–300 characters, top MAX_RESULTS = 2) because everything the tool returns gets spoken aloud, not displayed.

core/tool.py

The result is handed back with run_llm=True

params.result_callback(result, properties=FunctionCallResultProperties(run_llm=True)) both appends the tool's output to the shared context and tells Pipecat to immediately re-run the LLM on the updated context — so the model turns the raw scheme data into a short, spoken sentence without waiting for the caller to speak again.

core/prompt.py

The reply is deliberately short

The prompt caps the first reply to one or two schemes and a single line each, then asks the caller what they want next — every later turn reveals just one further detail (benefit, eligibility, documents, or how to apply), matching how a real phone conversation is actually paced.
